Error handling (haas-app/src/errors.ts) (Last Updated: 10/08/26)

***errors.ts defines the app's error types, much like a small Java exception hierarchy. 

**AppError:
extends the built-in Error and is the base class, so a component can catch every error we expect
with one type. 

**ValidationError is thrown in the browser before any request is sent, when user
input breaks a rule (empty, too short, bad characters, a quantity <= 0 or above what is available).
It holds a list of issues, each pairing a field (userID, password, projectID, quantity) with a
message; its summary message joins them all, and messageFor(field) returns the first message for
one input box. 

**ApiError is thrown by api.ts when the Flask server rejects a request, and carries
the HTTP status, with helpers isAuth() (401/403), isNotFound() (404), isConflict() (409, e.g.
someone else took the units first, so refetch hardware info and retry) and isServer() (5xx).

**NetworkError is thrown by api.ts when no answer comes back at all: the server is down, the
network dropped, or the request took longer than REQUEST_TIMEOUT_MS (8 seconds). Unlike ApiError
it has no HTTP status. Nolan first wrote it in api.ts; on 10/08/26 it moved into errors.ts so every
error type lives in one file, and api.ts and api.test.ts now import it from errors.ts.

The rules that decide when to throw a ValidationError live in validation.ts, not in errors.ts. In
a component, call the validator and then the API inside one try block, and in the catch pass the
error to errorMessage(err, "fallback text") to get the string to display. The backend repeats
every check, so handle ApiError and NetworkError even when local validation passed.

Validation (haas-app/src/validation.ts) (Last Updated: 10/08/26)

***validation.ts holds the input rules. errors.ts says what an error is; validation.ts decides when
one is thrown.

**Rule constants at the top: MIN_USERID_LENGTH, MIN_PASSWORD_LENGTH, MIN_PROJECT_ID_LENGTH and
ALLOWED_CHARS (letters and digits only, used for userIDs and project IDs). The lengths are still 0
as placeholders until we agree on real values with the backend team; both sides must use the same rules.

**Private check functions (checkRequired, checkUserID, checkPassword, checkProjectID, checkQuantity)
each return a message for the first rule broken, or null. They never throw. checkRequired is the
shared "<label> is required!" check that the others call first, so every form uses the same wording.

**Exported validators are what components call. Each throws a ValidationError if anything fails:
- validateCreds(userID, password, mode): mode "signIn" only checks that both fields are filled in
  (the server decides whether they are correct, and older accounts keep working if the rules get
  stricter); "signUp" applies the full rules. Both fields are always checked, so the user sees
  every problem at once.
- validateProjectID(projectID): for the Create and Join project forms.
- validateQuantity(value, max): max is the set's available count for check-out, or what the project
  holds for check-in.

**Tests: src/validation.test.ts covers sign-up and sign-in modes, project IDs and quantities
(npm test, all 39 tests passing). Add min-length tests once the real lengths are set.
