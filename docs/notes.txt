Error handling (haas-app/src/errors.ts) (Last Updated: 10/08/26)

***errors.ts has all of the app's error types. It's set up a lot like a small Java exception hierarchy.

**AppError extends the built-in Error and is the base class for the others, so a component can catch
any error we expect with just one type.

**ValidationError gets thrown in the browser before a request is ever sent, when the user's input breaks
a rule (empty, too short, bad characters, or a quantity that's <= 0 or more than what's available).
It holds a list of issues, where each one pairs a field (userID, password, projectID, quantity) with a
message. Its main message joins all of them together, and messageFor(field) gives you the first message
for a single input box.

**ApiError gets thrown by api.ts when the Flask server rejects a request. It carries the HTTP status and
has a few helpers: isAuth() (401/403), isNotFound() (404), isConflict() (409, e.g. someone else grabbed
the units first, so refetch the hardware info and try again), and isServer() (5xx).

**NetworkError gets thrown by api.ts when nothing comes back at all: the server is down, the network
dropped, or the request took longer than REQUEST_TIMEOUT_MS (8 seconds). Unlike ApiError, it doesn't have
an HTTP status. Nolan originally wrote it in api.ts. On 10/08/26 it got moved into errors.ts so all the
error types are in one file, and api.ts and api.test.ts import it from there now.

The rules for when to throw a ValidationError are in validation.ts, not errors.ts. In a component, call
the validator and then the API inside the same try block. In the catch, pass the error to
errorMessage(err, "fallback text") to get the string to show the user. The backend runs every check
again, so you still need to handle ApiError and NetworkError even if local validation passed.

Validation (haas-app/src/validation.ts) (Last Updated: 10/08/26)

***validation.ts has the input rules. Basically, errors.ts defines what an error is, and validation.ts
decides when to throw one.

**The rule constants are at the top: MIN_USERID_LENGTH, MIN_PASSWORD_LENGTH, MIN_PROJECT_ID_LENGTH, and
ALLOWED_CHARS (letters and digits only, used for userIDs and project IDs). The lengths are 0 for now as
placeholders until we settle on real values with the backend team, since both sides have to use the same rules.

**The private check functions (checkRequired, checkUserID, checkPassword, checkProjectID, checkQuantity)
each return the message for the first rule that's broken, or null if nothing is. They don't throw.
The others all call checkRequired first, which gives the "<label> is required!" message, so every form
uses the same wording.

**The exported validators are what components actually call. Each one throws a ValidationError if
anything fails:
- validateCreds(userID, password, mode): "signIn" mode only checks that both fields are filled in (the
  server decides if they're right, and this way older accounts still work if we make the rules stricter
  later). "signUp" mode applies all the rules. Both fields get checked every time, so the user sees all
  the problems at once instead of one at a time.
- validateProjectID(projectID): for the Create and Join project forms.
- validateQuantity(value, max): for check-out, max is how many units of the set are available. For
  check-in, it's how many the project holds.

**Tests: src/validation.test.ts covers sign-up and sign-in modes, project IDs, and quantities
(npm test, all 39 tests passing). Once the real lengths are decided, we need to add min-length tests.

Replies to Nolan's decisions list (below):

- Project ID validator: done (validateProjectID), but ProjectsView doesn't call it yet.
- validateCreds on the forms: the "signIn"/"signUp" modes are ready, but SignInView and NewUserModal
  don't use it yet.
- Check-in limit: still waiting on the backend to return how many units a project holds. Until then,
  HardwareSetCard passes Number.MAX_SAFE_INTEGER as the check-in max.

Math Class Creation and New Test Cases for User Input (10/09/26):

Both issues are fixed and the typecheck is clean. Lint didn't print a final result for me, so it should
be rerun to make sure.

The Math class: I added IntMath in a new file, src/math.ts. IntMath.parseInt(text) only accepts whole
numbers written as plain digits, with an **optional minus sign** and no leading zeros. Anything else
returns NaN, and the quantity check then shows "Quantity must be a whole number!". The minus sign is
allowed on purpose, so that -3 still gets the "greater than 0" message instead of a generic one. I called
it IntMath instead of Math so it doesn't shadow JavaScript's built-in Math.

So in the end, only plain whole numbers make it through: no blanks, 1e0, negatives, or leading zeros.

Blank input: HardwareSetCard.tsx now calls IntMath.parseInt(qty) instead of Number(qty). A blank field
turns into NaN instead of 0, so validateQuantity rejects it.

One message changed: in validation.ts, the error for a NaN quantity now says "Quantity must be a whole
number!" instead of "Quantity must be a number!". NaN now covers things like 2.5 and 1e0 too, so the old
wording didn't really fit anymore. I updated validation.test.ts to match.

The new tests are in src/math.test.ts. After the first fix all 58 tests passed, and after adding the
leading-zero rule all 60 pass.

I also went through the frontend and the mock API looking for every place where text gets turned into a
number. There's only one place where a user actually types a number, and it already goes through IntMath:

- src/components/HardwareSetCard.tsx:19 - the Quantity box on each hardware card. It's the only number
    input anywhere in the app, and it uses IntMath.parseInt(qty).
- mock-api.ts:96 - the mock server reading quantity from the request body. This one doesn't use math.ts.
    It does Number(b.quantity) and then checks that the result is a whole number above 0.
- mock-api.ts:146 - the ?seconds= param on the dev-only /__mock/outage route that fakes a server outage.
    It doesn't use math.ts either, but it isn't user input.

I didn't add anything for decimals. No field in the app takes one, so math.ts only has IntMath. A decimal
parser would just be code nobody uses yet.

There's one small gap in the mock API. The page always sends quantity as an actual number, so a normal
user can't run into this. But if something sends it as the string "1e0", Number() turns that into 1 and
the mock accepts it. I can't reuse IntMath there, because IntMath parses typed text and the request body
already has a number in it. The fix is a one-line check that quantity really is a number and not a string.
