# EE 461L — HaaS Proof of Concept

Team project for UT Austin EE 461L (Software Engineering and Design Laboratory), Fall 2026, Dr. Abhay Samant. A Hardware-as-a-Service web app: user/project management with encrypted credentials, and checkout/check-in of HWSet1 and HWSet2 against a shared database.

## Sourcing rules

Course honor code applies to everything in this repo.

- **No code copied from the web.** Not from Stack Overflow, blog posts, tutorial repos, GitHub projects, or gists — and not paraphrased out of them. Write from the problem, from official library documentation, or from class slides. Attribute slide-derived code in a comment.
- **Using a library is not copying.** Installing Flask, React, `pymongo`, `bcrypt`, or pytest and calling their documented APIs is the assignment. Following official docs is fine.
- No code from other students or from prior semesters.
- **Keep this repository private.** Course solution code must not be published, during or after the semester.

## Stack

- Backend: Python + Flask
- Frontend: React.js
- Database: MongoDB
- Tests: pytest (and Postman for API checks)
- Containers: Docker
- Deploy: cloud free tier, reachable by URL

A deviation from this stack needs TA sign-off first.

## Project conventions

- **No hard-coded data on pages.** User, project, and hardware information is read from the database through the API. This is a graded requirement (R2-2), not a style preference.
- Credentials are hashed, never stored or logged in plaintext. No secrets in the repo — use environment variables and keep `.env` out of version control.
- Branch and open a PR rather than committing to `main`.
- Issues and user stories live on **separate** GitHub project boards.
- Instructor and TAs are collaborators on this repo; write commit messages and comments accordingly.

## Working with this codebase

- When implementing a nontrivial piece, state the design decision and why in the PR description. Midterm 2 asks each student to explain the team's modularization, encapsulation, and refactoring choices from memory.
- Prefer small, reviewable changes over large sweeping ones.
- Don't add dependencies without a reason that holds up; keep the toolchain minimal.
